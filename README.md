# Лабораторная работа №1

## Подготовка окружения

Запустите кластер и окружение:

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

Создайте в корне репозитория файл `.env.local` и добавьте параметры, которых нет в сгенерированном `.env` (.env.local содержит дополнительные настройки сервиса, чтобы они не терялись при повторной генерации .env):

```dotenv
HTTP_READ_TIMEOUT=10s
HTTP_READ_HEADER_TIMEOUT=5s
HTTP_WRITE_TIMEOUT=15s
HTTP_IDLE_TIMEOUT=60s
HTTP_MAX_BODY_BYTES=1048576
DATABASE_ROLLBACK_TIMEOUT=3s
IDEMPOTENCY_TTL=24h
```

Примените миграции:

```bash
make migrate
```

Запустите сервис:

```bash
make run
```

| Переменная | Назначение | Пример |
|---|---|---|
| `HTTP_ADDR` | Адрес HTTP-сервера | `:8080` |
| `HTTP_READ_TIMEOUT` | Таймаут чтения запроса | `10s` |
| `HTTP_READ_HEADER_TIMEOUT` | Таймаут чтения заголовков | `5s` |
| `HTTP_WRITE_TIMEOUT` | Таймаут записи ответа | `15s` |
| `HTTP_IDLE_TIMEOUT` | Таймаут простаивающего HTTP-соединения | `60s` |
| `HTTP_MAX_BODY_BYTES` | Максимальный размер тела создания поездки, байты | `1048576` |
| `LOG_LEVEL` | Уровень логирования: `debug`, `info`, `warn`, `error` | `info` |
| `SHUTDOWN_TIMEOUT` | Общий бюджет остановки HTTP и ожидания закрытия пула | `10s` |
| `DATABASE_URL` | Строка подключения PostgreSQL | Значение из окружения |
| `DATABASE_MAX_CONNS` | Максимальное число соединений пула | `10` |
| `DATABASE_MIN_CONNS` | Минимальное число соединений пула | `2` |
| `DATABASE_MAX_CONN_LIFETIME` | Максимальное время жизни соединения | `30m` |
| `DATABASE_CONNECT_TIMEOUT` | Таймаут подключения и стартовой проверки БД | `5s` |
| `DATABASE_QUERY_TIMEOUT` | Таймаут операции репозитория, `BEGIN`, `COMMIT` и проверки readiness | `3s` |
| `DATABASE_ROLLBACK_TIMEOUT` | Таймаут отката транзакции | `3s` |
| `IDEMPOTENCY_TTL` | Срок действия ключа идемпотентности | `24h` |

## Решения

### Менеджер транзакций

Бизнес-код использует интерфейс:

```go
type TxManager interface {
    Do(ctx context.Context, fn func(context.Context) error) error
}
```

Внешний `Do` открывает транзакцию и сохраняет её в контексте. Репозиторий выбирает исполнителя через `Executor`:

- транзакцию из контекста, если она присутствует;
- пул, если репозиторий вызван вне `Do`.

Если callback вернул `nil`, выполняется коммит. При ошибке выполняется откат. При панике отложенный откат также выполняется, после чего паника продолжает распространяться.

Вложенный `Do` использует существующую транзакцию и не управляет её завершением. Ошибка вложенного вызова должна возвращаться наружу, чтобы внешний Do откатил общую транзакцию.

Создание поездки и запись её начального статуса выполняются в одной транзакции. Завершение поездки и запись перехода статуса также атомарны.

### Уровень изоляции

Используется `READ COMMITTED`, явно заданный при открытии транзакции.

Для текущих операций он достаточен: конкурентное создание защищается уникальным индексом, а завершение - условием в самом `UPDATE`.

### Одна активная поездка на водителя

В миграции создан частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX trips_one_active_per_driver_idx
ON trips(driver_id)
WHERE status = 'active';
```

Он обеспечивает ограничение и при параллельных запросах.

Репозиторий преобразует ошибку PostgreSQL `23505` в `ErrDriverBusy` только при совпадении имени этого индекса



### Конкурентное завершение

Обновление выполняется с условием:

```sql
WHERE id = $1 AND status = 'active'
```

Если обновлена строка, сервис записывает историю завершения в той же транзакции.

Если обновлено ноль строк, сервис читает поездку:

- отсутствие означает `trip_not_found`;
- существующая поездка означает `trip_completed`.

При двух конкурентных завершениях одна транзакция обновляет строку, а другая после ожидания проверяет условие повторно. После успешного коммита первой транзакции вторая не перезаписывает `finished_at`.

### Идемпотентность создания поездки

Ключи хранятся в PostgreSQL в таблице `trip_idempotency` вместе
с SHA-256 от параметров запроса, идентификатором поездки и временем
истечения.

Срок действия ключа задаётся переменной `IDEMPOTENCY_TTL`.

Транзакционная advisory-блокировка
по ключу предотвращает одновременную обработку одного ключа:
конкурентный запрос ждёт завершения первого, затем проверяет
сохранённый результат.

## Запуск в Docker

Перед запуском поднимите окружение с PostgreSQL и подготовьте
`.env` и `.env.local`, как описано выше.

Соберите образ из корня проекта:

```bash
docker build -f deploy/Dockerfile -t trip-service:lab1 .
```
Запустите сервис:
```bash
docker run --rm \
  --env-file .env \
  --env-file .env.local \
  --add-host=host.docker.internal:host-gateway \
  -p 8080:8080 \
  -e 'DATABASE_URL=postgres://tripgo:tripgo@host.docker.internal:21032/tripgo?sslmode=disable' \
  trip-service:lab1
```

Размер образа: 21.5MB
